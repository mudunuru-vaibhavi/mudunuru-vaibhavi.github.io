Self-healing Epic Clarity ETL

A nightly pipeline from Epic Clarity to a SQL warehouse that checks everything before it loads, sends an agent to investigate failures, and ends in one dashboard for executives, finance, data and IT.

Questions it answers

  • Did last night's load land, and if not, exactly why?

The problem

Hospitals report from Epic's Clarity database, which a data team copies every night into its own warehouse. When that copy breaks, someone has to find out why at 2 AM: a file cut short in transfer, a column Epic added after an upgrade, rows pointing at visits that were never sent. Until it is fixed, every report downstream is a day stale, and loading bad data is worse than loading none.

This project rebuilds that whole path as a working proof of concept, then adds an agent that does the first hour of on-call investigation.

How it works

  1. Source: Clarity extracts. A day-by-day simulation of a fictional health system writes pipe-delimited files and a checksum manifest every night.
  2. Transfer: SFTP landing. New drops are pulled only once their manifest exists, into a temporary folder renamed into place.
  3. Check, then load. Checksum, row count, schema and types first; then duplicate keys, required fields, foreign keys and balance reconciliation in SQL.
  4. Investigate failures. The agent reads the audit log, inspects files and queries the warehouse read-only. It may only re-pull and retry; anything else needs a person.
  5. Report. Reporting marts rebuild after each run and feed one dashboard with four audiences.

Each night loads in one transaction: all of it, or none of it. A failed night holds every later night, because an incremental extract can't be applied before the one it builds on. Every run, file, check and incident is logged, and those audit tables power the IT and data-quality views.

Two nights the agent handled

Nov 11 · resolved in 4 minutes · no human needed. A transactions file was cut short on its way over SFTP. The landed file failed its checksum. The agent compared it with the source, found the source copy intact, re-pulled the drop and retried. The night loaded, and the incident closed itself.
Nov 14 · held for approval. Epic added a PAT_EMAIL column to the patient extract. The agent matched the new header against the agreed contract, profiled the new column without copying any values into its report, and flagged it as likely PHI under HIPAA's minimum-necessary rule. It held all later nights and asked a person to decide. When a clean file was re-sent, the pipeline caught up on its own.

Design decisions

  • A contract, not a guess. A schema registry lists every expected column, type, key and foreign key, so an upstream change becomes a reviewed decision instead of a silent break.
  • Two safe actions only. Re-pull and retry can't damage data. Everything else is written up as an incident with the exact change proposed.
  • Tested on the real thing. CI pushes three weeks of drops to a real SFTP container, loads them into SQL Server 2022, breaks one night, and checks that it heals.
